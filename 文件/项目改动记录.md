## 三、改动历程（按时间顺序）

### Phase 1: 代码阅读与分析
- 克隆原始仓库, 阅读 `DDPG/` 下所有 `.py` 文件
- 原始代码: 单 UAV, 单用户, TensorFlow 实现
- 确认了 state/action/reward 定义、运动模型、信道模型

### Phase 2: 多 UAV 环境构建 (需求 1-6)
**改动文件**: `config.py`, `UAV_env.py`, `ddpg_agent.py`, `train.py`, `state_normalization.py`

核心改动:
1. **多 UAV 支持**: K 架 UAV 独立运动, 各自有电池、位置
2. **多用户关联**: 距离优先贪心算法, 每架 UAV 最多服务 N_MAX 个用户
3. **算力平均分配**: `f_ik = F_UAV / N_k`, `b_ik = BW / N_k`
4. **动作空间**: `[θ_0, v_0, ..., θ_{K-1}, v_{K-1}, x_0, ..., x_{M-1}]`
5. **状态空间**: `[电池×K, UAV坐标×2K, UE坐标×2M, 任务量×M, 时隙进度]`
6. **延迟模型**: T_i = max(T_local, T_trans + T_edge_comp)
7. **奖励**: ρ = Σ(1 - T_i / T_baseline)
8. **框架**: TensorFlow → PyTorch

### Phase 3: 训练稳定性优化
**问题**: 过早收敛, reward 平台期, UAV 不移动

解决方案:
1. **Warmup 阶段**: 前 2000 步纯随机, 填充 Replay Buffer
2. **移除 Reward Normalizer**: 防止梯度消失
3. **超参数调优**: LR_ACTOR=1e-4, LR_CRITIC=1e-3, TAU_SOFT=0.001
4. **边界反弹**: 替代 clip, 防止 UAV 卡边界
5. **距离奖励**: Proximity bonus 鼓励 UAV 靠近用户 (后来去掉了)
6. **时隙进度**: 状态加入归一化时隙编号

### Phase 4: 可视化构建
**新建文件**: `visualize.py`

5 张图:
1. Training Curves (Reward / Delay / ρ)
2. UAV Trajectory (带步号箭头)
3. Association Snapshot (用户-UAV 关联线)
4. Episode Details (延迟/ρ/奖励/电池/充电)
5. Baseline Comparison (DDPG vs Random vs All-Local vs All-Offload)

### Phase 5: WCT 无线充电模型 (需求 7)
**改动文件**: `config.py`, `UAV_env.py`, `visualize.py`

论文公式实现:
- eq.9: 3D 距离 `l = sqrt(Δx² + Δy² + (H-H_c)²)`
- eq.10: 充电功率 `P = η / (θl + μ)²`, l ≤ L_c
- eq.11: 多 WCT 功率叠加 `P_total = Σ P_j`
- eq.12: UAV 接收上限 `P_in = min(P_total, P_th)`
- eq.13: WCT 输出约束 `Σ P_k ≤ P_max`
- eq.14: 充电能量 `E_in = P_in × t_c`

电池更新: `E_new = E_old - E_out + E_in`

### Phase 6: 奖励优化
- 尝试归一化 (mean) → 用户反馈效果不好 → 改回求和 (sum)
- UAV 初始位置: 固定均匀分布 → 随机化
- 充电参数: ETA 50→5000, 充电功率从 0.02W 提升到 ~2W
- 新增: 充电激励 + 低电量惩罚

### Phase 7: 算法创新 — 改进 DDPG 迭代过程

**目标**: 提出改进的 DDPG 算法, 比标准 DDPG 提升 ≥20%

#### 迭代 7.1: 纯 PER-DDPG (V1)

**改动**: 只将 Replay Buffer 从均匀采样改为 SumTree 优先采样
- PER_ALPHA = 0.6, PER_BETA_START = 0.4
- 网络结构不变, 确保公平对比

**结果 (500ep)**:

| 指标 | Standard DDPG | PER-DDPG V1 | 差异 |
|------|---------------|-------------|------|
| Reward | 269.01 | 264.10 | **-1.8%** ❌ |
| ρ | 0.450 | 0.440 | -2.2% |
| Delay | 7.96s | 8.08s | +1.5% |

**分析**: PER V1 反而**更差**, 原因:
1. α=0.6 太激进, 过度关注少数异常经验
2. β=0.4 IS 修正太弱, 偏差没消除
3. 优先采样导致 Critic 过拟合

#### 迭代 7.2: PER + TD3 (V2)

**改动**: 
1. α 降到 0.3 (温和优先)
2. β 提高到 0.6 (更早修正)
3. 加入双 Critic (TD3): min(Q1, Q2) 防止 Q 过估计
4. 目标策略平滑 + Actor 延迟更新
5. IS 权重裁剪 (max=5.0)

**结果 (500ep)**:

| 指标 | Standard DDPG | PER-DDPG V2 | 差异 |
|------|---------------|-------------|------|
| Reward | 270.27 | 272.78 | **+0.9%** ✓ 但不够 |
| ρ | 0.450 | 0.455 | +1.1% |
| Delay | 7.93s | 7.87s | -0.8% |

**分析**: 方向对了, PER V2 微弱领先, 但差距仅 ~1%, 远不够 20%

#### 迭代 7.3: PER + TD3 + N-step (V3)

**改动**: 在 V2 基础上加入 N-step Returns (n=3)
- NStepBuffer: 暂存 3 步, 计算累积折扣回报 R = r₁ + γr₂ + γ²r₃
- Critic target: y = R + γ³ Q(s₃, a₃)

**结果 (500ep)**:

| 指标 | Standard DDPG | PER-DDPG V3 | 差异 |
|------|---------------|-------------|------|
| Reward | 270.27 | 243.35 | **-10.0%** ❌ |
| ρ | 0.450 | 0.406 | -9.8% |
| Delay | 7.93s | 8.58s | +8.2% |

**分析**: N-step 大幅恶化! 原因:
1. N-step 累积 reward 改变了 target 量级, Critic 收到的 y 值偏大
2. 结合 PER 后, 高 TD-error 的 N-step 样本被过度采样
3. 需要对 N-step reward 做归一化, 或降低 Critic LR

#### 迭代 7.4: 回退到 V2 (PER + TD3), 去掉 N-step ✓

已确认 V2 版本 (PER + TD3) 结果:
- Reward: **275.52** vs 标准 267.54 → **+3.0%**
- ρ: **0.459** vs 0.446 → **+2.9%**
- Delay: **7.80s** vs 7.99s → **-2.4%**

### Phase 9: 凸优化算力分配 (DRL + 凸优化混合框架)

**改动文件**: `UAV_env.py`, `train_unified.py`, `plot_results.py`
**新增文件**: `test_cvx.py`

#### 背景

原来的算力分配方式是**均分**: `f_{k,i} = F_UAV / N_k` (UAV k 的算力平均分给 N_k 个用户)

问题: 用户任务负载差异大时浪费算力 — 轻负载用户分到和重负载一样多的算力

#### 凸优化解决方案

给定 UAV 位置和用户关联后, 算力分配问题是凸优化:

```
min  Σ_{i∈S_k} c_i / f_{k,i}     (最小化总计算延迟)
s.t. Σ_{i∈S_k} f_{k,i} = F_UAV   (算力总和约束)
     f_{k,i} > 0
```

其中 `c_i = x_i · D_i · C_i` 是用户 i 的卸载计算负载

**KKT 条件推导的闭式最优解**:
```
f_{k,i}* = F_UAV × √c_i / Σ_{j∈S_k} √c_j
```

直觉: **负载大的用户按根号比例分到更多算力**

#### 实现方式

`UAV_env.py` 新增 `use_cvx_alloc` 参数:
- `UAVEnv(use_cvx_alloc=False)` → 均分算力 (Baseline)
- `UAVEnv(use_cvx_alloc=True)` → 凸优化最优算力

`train_unified.py` 新增算法:
- `--algo ddpg_cvx` → DDPG + 凸优化
- `--algo per_ddpg_cvx` → PER-DDPG + 凸优化

#### 验证结果 (test_cvx.py)

单步对比 (50 个随机种子平均):
- Reward 提升: **+13.9%**
- Delay 降低: **-4.8%**

#### 训练对比 (500 episodes)

| 算法 | Reward (R_50) | ρ (R_50) | Delay (s) | vs DDPG均分 |
|------|---------------|----------|-----------|-------------|
| DDPG (均分) | 203.59 ± 4.16 | 0.339 | 9.53 | — 基准 |
| PER-DDPG (均分) | 205.94 ± 3.57 | 0.343 | 9.47 | +1.2% |
| DDPG (凸优化) | 225.46 ± 3.36 | 0.376 | 8.99 | **+10.7%** ✓ |
| PER-DDPG+CVX (Ours) | **228.48 ± 3.84** | **0.381** | **8.92** | **+12.2%** ✓ |

#### 系统框架升级

从"纯 DRL"升级为**"DRL + 凸优化"两层混合优化**:
- **第一层 (DRL)**: 决定 UAV 轨迹 + 卸载比例 (非凸/高维 → 深度强化学习)
- **第二层 (凸优化)**: 给定关联后求最优算力分配 (凸问题 → 闭式解)

## V13: 目标函数重设计 (归一化加权目标)

### 改动原因
之前充电奖励是拍脑袋的 `CHARGE_BONUS=0.3`，与建模目标函数脱节。
参照论文建模，将能耗纳入目标函数，使充电成为数学驱动的优化目标。

### 新目标函数 (论文公式)

$$\min \Phi = \omega_t \frac{\sum T_i^{off}}{\sum T_i^{loc}} + \omega_e \frac{\sum E_k^{net}}{\sum E_k^{consume}}$$

等价最大化奖励:

$$r(t) = \omega_t \cdot \sum_i \rho_i(t) + \omega_e \cdot \eta_E(t)$$

其中 η_E = E_charge / E_consume 为**能量回收率** ∈ [0,1]

### 代码改动

| 修改项 | 改前 | 改后 | 文件 |
|--------|------|------|------|
| 奖励结构 | ρ + CHARGE_BONUS - penalty | **ω_t×Σρ + ω_e×η_E - penalty** | UAV_env.py |
| 权重参数 | REWARD_RHO_WEIGHT, CHARGE_BONUS | **OMEGA_T=1.0, OMEGA_E=0.5** | config.py |
| 电池容量 | 20kJ | **40kJ** (够28步) | config.py |
| 环境版本 | V5 | **V6** | UAV_env.py |

### η_E 的物理意义

| UAV 位置 | 充电功率 | η_E | 效果 |
|---------|---------|-----|------|
| 远离 WCT | 0W | 0 | 只拿 ρ 奖励 |
| WCT 边缘 (100m) | 20W | 0.03 | 微弱 |
| WCT 附近 (30m) | 198W | 0.33 | 额外 +0.17 |
| WCT 正上方 | 200W | 0.34 | 额外 +0.17, 电量不降 |

### 实验数据 (obj_v13, E=40kJ, 2000eps)

| # | 算法 | Reward | ρ | Delay | Steps | 备注 |
|---|------|--------|---|-------|-------|------|
| 16 | Vanilla DDPG | 146.36 | 0.389 | 8.81s | ~31 | 方差大±14.87 |
| 17 | PER-DDPG+CVX | **191.88** | **待测** | - | **31** | 第31步没电死亡 |

**结论**:
- ✅ 死亡终止机制生效 (31步没电→提前结束)
- ✅ PER-DDPG+CVX 大幅领先 Vanilla (191 vs 146)
- ❌ 电量曲线无上升段, UAV 未学会充电
- ❌ η_E 奖励增量 (~0.17) 远小于飞去 WCT 导致的 ρ 损失 (~0.5+)

**下一步思考方向**:
- 增大 OMEGA_E (0.5→3.0+)? 让充电收益 > ρ 损失
- 或者重新思考 η_E 的定义和权重

## V16: 奖励归一化改造 (核心实验)

### 改动原因

分析发现奖励两项**量级严重失衡**:

| 分量 | 公式 | 范围 | 权重 | 实际贡献 |
|------|------|------|------|---------|
| 延迟缩减 | **Σρ_i** (求和, M=20) | [0, **20**] | ω_t=1.0 | ~8.0/步 |
| 能量回收率 | η_E | [0, 1] | ω_e=0.6 | 最大 0.6/步 |

η_E 只占总奖励 ~7%, UAV 没有动机牺牲 ρ 去充电!

### 解决方案

将 Σρ 改为 mean(ρ), 两项归一到 [0,1], 再乘 M 恢复量级:

$$r(t) = M \times [\omega_t \cdot \overline{\rho}(t) + \omega_e \cdot \eta_E(t)] - \text{penalty}$$

改后两项量级对比:

| 分量 | 范围 | ×M 后 | 占比 |
|------|------|-------|------|
| mean(ρ) | [0, 1] | [0, 20] | ~63% |
| η_E | [0, 1] | [0, 12] | ~37% |

### 中间失败: 不乘 M (V16a, 未记录)

直接用 `r = ω_t × mean(ρ) + ω_e × η_E`, 每步奖励仅 ~0.4, Q 值量级从 ~67 骤降到 ~3.8, 梯度信噪比崩溃, 3000eps 完全不学习 (R=8, ρ=0.329)

### V16 实验数据 (乘 M 版, obj_v16, 3000eps)

| # | 算法 | Reward | ρ | Delay | Steps | 备注 |
|---|------|--------|---|-------|-------|------|
| 22 | PER-DDPG+CVX | 198.92±50.60 | 0.335 | 9.583s | ~32 | 仍未学会充电 ❌ |

**结论**: 归一化后 η_E 占比提升到 37%, 但 ρ 反而从 0.418 降到 0.335, 说明**单纯调权重无法解决充电问题**

## 充电行为未学会 — 根因分析 (待讨论)

### 核心矛盾

| 行为 | 即时奖励 | 长期收益 | DRL 是否容易学到 |
|------|---------|---------|----------------|
| 靠近用户群 | ρ 高 (~0.4) | — | ✅ 容易 |
| 飞去 WCT 充电 | ρ 低 (~0.2) | 多活 9 步 | ❌ 极难 |

### 三大障碍

1. **空间冲突**: WCT 在场地四角 (125,125 等), 用户随机分散全场. 飞去 WCT ≈ 远离用户 → ρ 大降
2. **探索困难**: 需要连贯的多步探索序列 (飞去→停留→飞回), 高斯噪声做不到
3. **延迟归因**: 充电的好处 (多活 9 步) 要到 episode 末才体现, credit assignment 困难

### 数值验证

不充电: 31 步 × 8/步 - 死亡惩罚 ≈ **~192**
充电 (理想): 40 步 × 7/步 ≈ **~280** (但需要发现这条路径)

理论上充电值得, 但 DRL 需要**先偶然发现** "充电→存活" 的因果链, 这在随机探索中几乎不会发生.

### 待讨论方案

| 方案 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| **A: 大幅增 ω_e** | OMEGA_E=3.0~5.0 | 简单 | 可能压过延迟目标 |
| **B: 动态权重** | 低电量时 ω_e 自动增大 | 符合直觉 | 不够优雅, 人为塑形 |
| **C: 距离引导** | 低电量时加入 "距 WCT 距离" 奖励项 | 直接引导 | 过度人为设计 |
| **D: 增大电池** | E=80kJ, 不死 | 绕开问题 | 充电变锦上添花 |
| **E: WCT 移到用户密集区** | 充电时也能服务用户 | 消除冲突 | 不符合实际场景 |
| **F: 分层 RL** | 高层决定 "服务/充电" | 结构化 | 实现复杂 |

### 关键问题 (问老师)

1. 论文是否必须展示 "UAV 学会主动充电" 的行为? 还是只要有充电模型即可?
2. 如果必须学到充电, 是否允许 reward shaping (方案 B/C)?
3. 是否可以调整场景设定 (方案 D/E) 让充电更容易学到?

## UAV 轨迹无意义 — 建模层面的根本问题 (2026-04-15 发现)

### 问题描述

当前模型中 UAV 没有移动的动机:

| 因素 | 当前设定 | 后果 |
|------|---------|------|
| 用户移动性 | V_UE=1m/s → 每时隙最多 8m | 在 500m 场地里几乎不动 |
| 任务分布 | 所有 M=20 用户每时隙都有任务 | 无时空变化 |
| 任务大小 | 均匀 [2.5, 3.0] Mbits | 无空间差异 |
| 飞行代价 | P_fly(v) > P_hover (飞行耗更多电) | 不飞反而省电 |

**结论**: UAV 的最优策略是找到一个好位置后**悬停不动**, "轨迹优化"实际上毫无意义!

### 这也解释了充电不学习的问题

如果 UAV 天然倾向不动, 那更不会主动飞去 WCT 充电 — 这需要**大幅度移动**, 和 "悬停最优" 的策略完全矛盾.

### 候选修复方案

#### 方案 1: 增强用户移动性
- V_UE 从 1 → **5~10 m/s** (行人/车辆速度)
- 或用**群组移动模型 (RPGM)**: 用户分群, 每群有移动方向
- 效果: 用户群位置每隔几个时隙就大幅变化, UAV 必须追踪

#### 方案 2: 任务随机到达 (泊松模型)
- 每时隙只有 **30~50%** 的用户产生任务 (不是全部都有)
- 不同时隙 "热点区域" 不同, UAV 需要飞去任务密集区
- 更符合实际: 突发计算需求, 不是所有用户一直在算

#### 方案 3: 服务公平性约束
- 要求每个用户在 episode 内至少被服务 N_min 次
- UAV 不能蹲在一个角落, 必须巡逻覆盖全场
- 可加入 Jain's fairness index 作为评价指标

#### 方案 4: 充电驱动 "服务-充电" 循环 ⭐
- 电池足够小 → UAV **必须**定期飞去 WCT 充电
- "服务区" 和 "充电区" 在**不同位置** → UAV 被迫往返
- **同时解决充电问题和轨迹问题**
- 不是 DRL "发现" 充电有用, 而是**不充电就死**

#### 方案 5: 组合方案 (推荐) ⭐⭐
**任务随机到达 + 充电驱动**:
- 每时隙 50% 用户有任务 (Poisson 到达) → 创造空间变化, UAV 需追踪热点
- 电池够 20~25 步 → UAV 必须中途充电 → 创造服务↔充电往返轨迹
- WCT 与用户分离 → 自然形成 "服务区 → WCT → 服务区" 的周期性轨迹

### 方案对比

| 方案 | 轨迹有意义 | 解决充电问题 | 实现难度 | 论文故事性 |
|------|-----------|------------|---------|-----------|
| 1. 增强用户移动 | ✅ | ❌ | 低 | 一般 |
| 2. 任务随机到达 | ✅ | ❌ | 中 | 好 |
| 3. 公平性约束 | ✅ | ❌ | 中 | 好 |
| 4. 充电驱动循环 | ✅ | ✅ | 低 | **很好** |
| **5. 任务+充电组合** | **✅** | **✅** | **中** | **最好** |

### 需要和老师讨论

1. 论文是否需要 UAV 轨迹有实际意义 (动态追踪), 还是只要有合理的飞行路径即可?
2. 如果改成任务随机到达, 奖励函数是否需要调整 (不是所有用户都有 ρ)?
3. 倾向用哪种方案? 方案 4 (纯充电驱动) 最简单且效果明确

### 改动清单

| # | 文件 | 改动 | 改前 | 改后 | 原因 |

- 高斯: 连续 5 步同方向概率 0.5⁵=3%
- OU(θ=0.15): 上一步噪声 85% 保留, 连续同方向概率 >50%

| `moderately_separated` | 中等分离 | 用户在四个边中点热点分布，与 WCT 保持中等距离 |
| `strongly_separated` | 强分离 | 用户集中在场地中心，WCT 在四象限，形成最强空间冲突 |

### 代码改动

| 文件 | 改动 |
|---|---|
| `UAV_env.py` | `UAVEnv.__init__` 新增 `scenario` 参数；新增 `_validate_scenario`、`_sample_hotspot_users`、`_init_ue_positions`；`reset()` 中 UE 初始化切换为按场景采样 |
| `train_unified.py` | 新增 CLI 参数 `--scenario`；`run_experiment(...)` 增加 `scenario` 入参并透传给环境；结果 `.npz` 增加 `scenario` 字段 |

### 使用方式

```bash
python train_unified.py --algo per_ddpg_cvx --episodes 3000 --tag obj_v24_overlap --scenario overlapped
python train_unified.py --algo per_ddpg_cvx --episodes 3000 --tag obj_v24_midsep --scenario moderately_separated
python train_unified.py --algo per_ddpg_cvx --episodes 3000 --tag obj_v24_strongsep --scenario strongly_separated
```

### 预期现象

随场景从 `overlapped` → `moderately_separated` → `strongly_separated`，服务-充电空间冲突应逐步增强，策略更容易体现“延迟收益 vs 生存收益”的权衡。

## 八、创新点总结 (写论文用)


1. **系统建模创新**: 多 UAV-MEC 与 WCT 无线充电联合优化, 同时考虑轨迹/卸载/充电
2. **算法创新 (PER+TD3)**: 优先经验回放 + 双 Critic 防止过估计 + 延迟策略更新
3. **混合优化框架 (DRL + 凸优化)**: DRL 解决非凸轨迹规划, 凸优化求最优算力分配
4. **凸优化闭式解**: KKT 条件推导, 无需迭代, 计算开销 O(N_k)
